# Module 02: Understand Azure Databricks architecture

Module link: https://learn.microsoft.com/en-us/training/modules/understand-azure-databricks-architecture/

Part of: [Set up and Configure an Azure Databricks Environment](../paths/set-up-and-configure-environment.md)

## Overview

- Units: 7 (introduction, three storage units, knowledge check, summary)
- Prerequisites: basic cloud storage concepts, familiarity with Azure Databricks workspaces, and Unity Catalog basics
- Why it matters: architecture decides where data lives, how compute runs, and how security is set up

## Learning objectives

1. Describe the account hierarchy and how it organizes resources.
2. Explain the difference between the control plane and the compute plane.
3. Understand workspace storage.
4. Describe default storage in serverless workspaces.
5. Explain how external locations connect cloud storage to Unity Catalog.
6. Understand how Unity Catalog managed storage organizes data.

## Key points

### 1. Account hierarchy

- **Account:** the top level. You manage identity, workspaces, Unity Catalog metastores, billing, and policies here.
- **Metastore:** the top-level metadata container in Unity Catalog. It is region-specific. Workspaces attached to the same metastore share one view of the data.
- **Workspaces:** created inside an account. Each one is isolated but shares account-level governance.
- **Hive metastore (legacy):** a workspace-level store. It appears as a catalog named `hive_metastore`. Microsoft recommends moving to Unity Catalog.
- The Unity Catalog namespace is `catalog.schema.object`.

### 2. Control plane and compute plane

- **Control plane:** runs the backend services, the web app, orchestration, job scheduling, and cluster management. It **does not process your data**.
- **Compute plane:** where data processing happens.
  - **Serverless compute:** runs in the Azure Databricks account, not in your subscription. Azure Databricks manages the infrastructure and scaling.
  - **Classic compute:** runs in your own Azure subscription, inside the workspace's virtual network. You get more control over networking and security.
- Classic workspaces are called **Hybrid workspaces** in the Azure portal.

### 3. Workspace storage

- **Classic workspaces** have a workspace storage account in your subscription.
- **Serverless workspaces** use **default storage**, which is managed by Azure Databricks inside the account.
- Workspace storage holds two kinds of data:
  - **Workspace file system data:** notebooks, SQL queries, dashboards, alerts, repos, libraries, and small config files.
  - **Workspace system data:** generated by the platform, such as query results, job results, notebook revisions, query plans, and cluster logs.
- Users reach this data through Unity Catalog and do not get direct access to the storage.
- **DBFS root and DBFS mounts are legacy and deprecated.** Use Unity Catalog tables and volumes instead.
- Security tip: turn on firewall support for the workspace storage account.

### 4. Unity Catalog managed storage

- **Managed storage** is where Unity Catalog keeps data for managed tables (tabular data) and managed volumes (files such as images or logs).
- Unity Catalog controls the full lifecycle: where data goes, how it's organized, and when it's deleted.
- You can set a storage location at three levels: metastore, catalog, or schema.
- **Catalog-level storage is the recommended choice.** Use schema-level storage when you need more control.
- When you create a managed table or volume, Unity Catalog checks the schema first, then the catalog, then the metastore. If none has a location, you can't create it.
- Unity Catalog adds hashed subfolders (`__unitystorage/catalogs/<uuid>` or `__unitystorage/schemas/<uuid>`) to each storage root. You don't manage these paths.
- Unity Catalog rejects a new managed location that overlaps an existing managed location, external table, or external volume.
- **Dropping a managed table** keeps the files for 7 days, then they are permanently deleted.

### 5. Default storage (serverless)

- Default storage is fully managed object storage built into Azure Databricks. No cloud account or credentials are needed.
- It is used by both classic and serverless workspaces for internal features such as Data Classification, Anomaly detection, Clean Rooms, and Knowledge Assistant.
- **Creating new catalogs on default storage is only possible in serverless workspaces.** A new serverless workspace gets a default catalog on default storage automatically.
- Classic workspaces can use a default-storage catalog only if it is bound to them, and only with serverless compute.
- Access is controlled with SQL GRANT statements, not cloud RBAC.
- Catalogs on default storage are accessible from the workspace where they were created unless you bind them to other workspaces.
- Dropped managed tables and volumes are cleaned up automatically.
- Default storage does not work for direct file access by external tools. BI tools can connect through ODBC or JDBC.
- Best fit: new serverless workloads and development. For production with external file access or classic compute, use external storage.

### 6. External locations and storage credentials

- An **external location** is a Unity Catalog object. It combines a cloud storage path with a **storage credential**.
- A **storage credential** is the authentication method. It is defined once and can be used by many external locations in the same security boundary.
- **Azure managed identities are the recommended option.** They need no secrets to rotate. Service principals work too, but you must manage client secrets yourself.
- Storage credentials are metastore-level objects.
- Supported storage: Azure Data Lake Storage (read and write, recommended for Azure Databricks), AWS S3 (read-only), and Cloudflare R2.
- External locations serve two purposes:
  - **External tables and volumes:** you manage the files. The data stays where it is.
  - **Managed storage locations:** Unity Catalog manages the data, in a location you choose.
- **Workspace binding** limits an external location or credential to certain workspaces. This applies even to privileged users. A common pattern is to use production credentials only in production workspaces.

## Exam focus

- Account, metastore, and workspace relationships. Metastores are account-level and region-specific.
- Control plane does not process data. Compute plane does.
- Serverless compute runs in the Databricks account. Classic compute runs in your subscription.
- Classic workspaces use a workspace storage account. Serverless workspaces use default storage.
- Storage location order: schema, then catalog, then metastore.
- DBFS root and mounts are deprecated.
- External location = storage path + storage credential. Use managed identities.
- Workspace binding restricts access by workspace.
